WATCHALL — IMPLEMENTATION LOG
=============================

This file keeps a short, human-readable record of the major fixes, features, and changes made to the WatchAll app.
Each entry explains what the problem or feature was, what changed, which files were affected, and how it was verified.
New entries are added at the bottom in chronological order. Older entries are never removed.

Date: 2026-10-27
Area: Stream extraction / playback reliability

Issue/Feature:
Some movies would not play because the extractor returned the first stream link it found without checking whether that link actually worked. Several Viduki CDN hosts were returning Cloudflare 522 errors or timing out, so the player was given a dead stream.

What changed:
The backend now checks each candidate stream before returning it. HLS links must return a valid playlist, DASH links must return a valid manifest, and MP4 links must respond to a small range request. Dead links are skipped and the search continues. The search time limit was extended, MP4-only titles get a short grace period, and manually switching to a dead server now returns a clear "server not responding" message. The player loading text now explains that it is finding a working server.

Files affected:
server/index.js
src/Pages/VideoPlayer.jsx

Verified:
Tested with Inception, an MP4-only title, and several other titles. Forced-server switching works, and forcing a dead server returns a clear 502 error. The build passes.

Date: 2026-10-27
Area: Search

Issue/Feature:
Search gave wrong or incomplete results for special characters and exact titles. "Fast & Furious" was effectively searched as only "Fast" because the search text was not encoded safely in the request, and the exact movie "Mrs." appeared on page 2 of TMDB's mixed search instead of page 1.

What changed:
Search text is now encoded correctly, so symbols such as "&" no longer break the request. Results from TMDB's movie, TV, and mixed searches are now combined, duplicates are removed, and results are ordered so an exact title match comes first, followed by titles that start with the search text, then partial matches. Slow responses from older searches can no longer overwrite the results of a newer search.

Files affected:
src/Services/api.jsx
src/Components/SearchBar.jsx

Verified:
In the running app, "Mrs." now returns the exact movie first, and "Fast & Furious" returns the correct 2009 film first. Other searches such as "Mr. & Mrs. Smith", "Spider-Man", "Drishyam 2", and "3 Idiots" also ranked correctly. The build passes.

Date: 2026-10-27
Area: Stream server selection / language

Issue/Feature:
Hindi titles were being played from English servers first, which could give the wrong audio. The desired behavior is to try all Hindi servers first and only fall back to the other servers if no Hindi server can play the title.

What changed:
The player now checks the title's original language in TMDB and sends it to the extractor. For Hindi titles, the backend rewrites Viduki's server list so all HINDI servers (currently Chris, Wesker, and Grace) come first, followed by the remaining servers. The player still walks the list normally: if one Hindi server fails, it moves to the next Hindi server, and only after all Hindi servers fail does it continue to the English/Vietnamese servers. The server picker keeps its original order, and manual server switching is unchanged.

Files affected:
server/index.js
src/Pages/VideoPlayer.jsx

Verified:
3 Idiots and DDLJ played from Chris. A simulated Chris failure fell back to Wesker. Blocking all three Hindi servers made the player continue to Leon, Jill, Ada, Claire, and Sherry and still play. Inception (English) still played from Leon. Confirmed in the live app that /api/extract receives lang=hi for Hindi titles and lang=en for English titles. The build and server syntax checks pass.

Date: 2026-10-27
Area: Video player / stream proxy

Issue/Feature:
The watch page used an older third-party player and the backend only handled simple HLS playlists. It did not give us a consistent full-screen player, DASH support, reliable seeking through byte ranges, or server switching from inside the player.

What changed:
The movie watch page now uses a custom WatchAll player built specifically for this project. It fills the screen in black, keeps the rest of the site navigation out of the way, and adjusts its layout for phones, tablets, desktop, and browser-based TVs. It includes a seek bar, play and pause, 10-second skip buttons, volume, auto-hide controls, keyboard shortcuts, mobile gestures, captions, playback speed, quality selection, server switching, retry messages, loading states, and fullscreen/picture-in-picture where the browser supports them. It also remembers your volume, captions, quality preference, and playback position. Media Session support lets phone and system controls work with the player. Focus is trapped inside the settings and help panels, Escape closes them, and TV remotes can move between controls with the arrow keys.

The backend now understands both HLS and DASH. It rewrites HLS playlists and DASH manifests so every key, initialization file, playlist, and segment goes back through the local proxy. It supports byte-range requests, which makes seeking work properly, and it caches recent media so replays and short seeks do not download the same data again. The proxy accepts both the original query format and the newer encoded path format, reports content type through a media-info endpoint, and allows the port to be changed with a PORT setting.

During testing we found and fixed a DASH issue where the supported track-change event name was different from the one being used. That error was stopping DASH playback before it started. DASH BaseURL handling was also corrected so nested and relative base addresses resolve to the right CDN files. The production backend was restarted so it is now running this code.

Verified:
The production build passes. The new player files pass ESLint, and the backend passes Node's syntax check. The restarted backend returned a valid DASH manifest rewrite, a working HLS playlist rewrite, and a 206 byte-range response for a DASH segment. Headless browser tests played both a public DASH stream and a public HLS stream, including the desktop, mobile, and TV layouts. Settings and help panels kept keyboard focus inside, closed with Escape, and produced no page errors. The real watch page was tested with Fight Club (TMDB 550): it loaded metadata from TMDB, extracted a working stream from Sherry, played the video, and displayed the custom controls. Date: 2026-10-28
Area: Deployment / Stream playback

Issue/Feature:
The app needed a separate computer running the Express/Puppeteer backend, which made a free deployment difficult. The goal was to host everything on Vercel for free while keeping stream extraction and playback working.

What changed:
A full backup of the working version was created first. It can be restored at any time from the local Git branch "backup/pre-vercel-only", the tag "backup-pre-vercel-only-2026-10-28", or the copies in ".backups/pre-vercel-only".

The backend can now connect to Browserless, a cloud browser service, using the BROWSERLESS_TOKEN setting. It defaults to Browserless's London stealth endpoint with a 110-second session limit. Local development still launches the installed Chrome, so no Browserless account is needed locally. On Vercel, a missing token produces a clear error instead of trying to start a browser that is not installed.

The Express app is now exported from server/index.js, and the local listener only starts when the file is run directly. The new api/index.js file exposes the same app as a single Vercel serverless function. A small api/package.json file marks the function folder as CommonJS so Vercel bundles the server code reliably even though the frontend package is an ES module. vercel.json sends every /api/* request to that function and sends all other routes to the React app.

The server list endpoint now returns a complete built-in list immediately instead of launching a browser on a cold start. The list is still refreshed automatically during normal extraction. Extraction time limits were shortened so a request fits inside Browserless's free two-minute session limit and the 120-second Vercel function limit.

In production, the player now plays the raw CDN stream URL directly, so video data no longer passes through any server. Local development keeps using the existing proxy so local playback still works. The proxy endpoint remains available as an optional fallback.

The backend packages were added to the root package.json because Vercel installs dependencies from the project root. An .env.example file, a .vercel ignore rule, ESLint settings for the server code and backup folder, and an updated server README were added.

Date: 2026-10-28
Area: Deployment / Browserless

Issue/Feature:
The deployed Vercel function failed with "Cannot find module 'puppeteer-extra-plugin-stealth/evasions/chrome.app'". Vercel's serverless bundler does not include the stealth plugin's dynamically loaded evasion files, so the function crashed before it could connect to Browserless.

What changed:
The stealth plugin is now loaded and applied only when the backend launches a local Chrome browser. On Vercel the backend connects to Browserless's own /stealth endpoint, which already provides anti-detection, so the local plugin is not needed there. Browserless connection errors are also returned with their real reason (for example 401) instead of a generic message, and the token is redacted in logs.

Files affected:
server/index.js
docs/IMPLEMENTATION_LOG.txt

Verified:
The server now loads without requiring any stealth evasion modules. A local request with an invalid Browserless token returned the clear 401 error instead of the missing-module crash. Backend syntax and lint checks pass.

Date: 2026-10-28
Area: Deployment / Stream extraction

Issue/Feature:
On the Vercel deployment, movie TMDB 1375156 ("Udta Teer") ended with the "No playable stream found" error after a long wait. The same movie worked on the local server, and Viduki's own player also played it. Other movies worked on Vercel.

What changed:
The extractor used to reject every stream that its own server-side reachability check could not fetch. On Vercel the function runs in a datacenter region (Washington, D.C. by default), and the Hindi CDN host that has the correct copy of this movie intermittently answers Cloudflare 520/522 to datacenter addresses. The local server runs in India, so its check succeeded. Viduki's player inside the browser had already loaded the stream correctly, but the extractor still threw it away and eventually reported that no stream existed.

The extractor now remembers which media files Viduki's player actually loaded with a successful response and accepts those immediately, without depending on the server-side check. The server-side check is still used for streams the browser has not confirmed, now with two attempts instead of one. The manual server-switch path uses the same rule, so switching to the Chris server no longer fails when only the Vercel-side check fails.

The Vercel function region was also set to Mumbai (bom1) so server-side checks run from India, close to the media hosts, instead of the default US region.

Files affected:
server/index.js
vercel.json
docs/IMPLEMENTATION_LOG.txt

Verified:
The local extraction log for TMDB 1375156 shows Viduki's player loading the Chris HLS stream and the server returning srv=Chris type=hls. The new logic accepts that stream because the browser loaded its manifest successfully. server/index.js passes Node's syntax check and ESLint, and the production build passes. The deployed fix still needs to be redeployed and tested with the same movie on Vercel.
